# Akole Taluka — Constituency Complaint Management & Analytics System

Built per the SRS for the Office of MLA Dr. Kiran Lahamte (Akole Taluka, Ahilyanagar).

Stack: **Node.js, Express, MongoDB (Mongoose), EJS, vanilla HTML/CSS/JS** — no React, no frontend framework.

---

## Render Blueprint deployment

The service definition is [render.yaml](render.yaml).

1. Twilio is included in the dependency manifest and lockfile. Commit both files
   so Render's `npm ci --omit=dev` installs the selected SMS provider.
2. Resolve the public-deployment issues documented in
   [ATLAS_RENDER_BLUEPRINT_GUIDE.md](../ATLAS_RENDER_BLUEPRINT_GUIDE.md), especially
   full MongoDB URI logging, registration OTP proof, private worker data/media,
   and the timeline response mismatch. Hosting configuration alone does not fix
   these issues.
3. Push approved source and the lockfile to your connected Git repository.
   Never commit the real `.env`, signing credentials, or private uploaded files.
4. In Render choose **New > Blueprint**, connect the repository, and select
   **Blueprint Path = `backend/render.yaml`** if the whole Android project is
   the repository root. The YAML's `rootDir: backend` is repository-relative,
   not relative to the YAML file.
5. If publishing only this backend's contents at repository root, remove
   `rootDir: backend` and use **Blueprint Path = `render.yaml`** instead.
6. Enter `MONGO_URI` (including your selected database), `TWILIO_ACCOUNT_SID`,
   `TWILIO_AUTH_TOKEN`, and `TWILIO_FROM_NUMBER` when prompted. Local `.env`
   values are not automatically copied to Render. Render generates `JWT_SECRET`.
7. Allow the service's **Connect > Outbound** IP ranges in Atlas Network Access,
   then retry deployment if the initial database connection failed.
8. Verify `/api/v1/villages`, real OTP delivery, and authenticated API calls.
   Set Android's base URL to the service's actual HTTPS URL plus `/api/v1/`,
   then rebuild the APK.

The build uses `npm ci --omit=dev`; keep the lockfile synchronized with the
manifest. No seed runs automatically: the existing Atlas demo data is retained.
The Blueprint does not provision MongoDB or a persistent disk. Free hosting
sleeps when idle, and uploads are temporary across restarts/redeployments.
Do not send real SMS to the seeded placeholder numbers. Use approved real test
numbers for SMS testing and replace demo privileged accounts before production.

The supplied YAML is a trial hosting definition, not production certification.
Render validates the Blueprint when it is connected; review any charges before
deploying.

## 1. What's implemented

### Twilio account settings and checks

This integration uses **Twilio Programmable Messaging**, not Twilio Verify.
Create/configure your own Twilio account; credentials cannot be generated by
this application. In the Twilio Console obtain the Account SID (starts with
`AC`) and Auth Token, then choose an approved SMS-capable sender number.
Enable the required destination permissions and confirm Indian SMS
sender/template/regulatory requirements with Twilio. Trial accounts may require
verified recipients; never send to the seeded demo placeholder numbers.

Privately configure these values in your local `.env`, or in Render's service
Environment settings. Do not commit real values:

<!-- // Generated by GitHub Copilot - Oct-17-2026 -->
```properties
OTP_MODE=twilio
TWILIO_ACCOUNT_SID=<your AC-prefixed Account SID>
TWILIO_AUTH_TOKEN=<your account Auth Token>
TWILIO_FROM_NUMBER=<your approved sender in +countrycode format>
```

From the backend directory, validate settings and run offline tests:

<!-- // Generated by GitHub Copilot - Oct-17-2026 -->
```powershell
npm run check:otp
npm run test:otp
```

The configuration check prints no credentials and sends no SMS. It checks
format/presence, not account ownership, authorization, sender approval, balance,
or delivery. The offline tests use a mocked provider and never send SMS.

Restart/redeploy after updating credentials. The server now refuses unknown OTP
modes, incomplete Twilio configuration, and console OTP in production. Isolated
development console mode remains available. Real SMS errors do not fall back
to demo codes. A queued message means provider acceptance, not confirmed delivery:
check the Twilio Messaging logs and the recipient phone for final delivery.
Failed send requests leave their saved challenge unusable.

For a live check, use the login page's **Send OTP** action once with your own
approved test number; this incurs provider charges and needs a working database.
Confirm SMS receipt, enter the code, and check `auth/me` after login. Twilio
provider failures are logged with sanitized numeric error codes, not raw provider
messages containing recipient details. Production rate limits, protected OTP
storage, and registration proof enforcement still require the separate hardening
documented in the deployment guide; this change does not claim to implement them.

- **Mobile OTP login** (Module 1.1) — OTP is generated server-side and, in the default
  `console` mode, printed to your terminal and returned in the API response so you can
  test end-to-end without a paid SMS provider. Swap `OTP_MODE=twilio` in `.env` and fill
  in `TWILIO_*` to send real SMS (the `twilio` npm package is included).
- **Worker registration** (Module 1.2) — mandatory Gram Panchayat selection from a
  pre-seeded ~178-village Akole Taluka master list (extend `seed/villages.js` with the
  official 190+ list when you have it, then re-run the seed).
- **Account verification toggle** (Module 1.3) — admin can verify/flag workers.
- **Complaint creation** (Module 2.1) — category dropdown, Marathi/English text (UTF-8),
  up to 3 photos (5MB each), a 60-second voice note recorded natively in the browser via
  `MediaRecorder`, GPS auto-capture via `navigator.geolocation`, and urgency selector.
- **Worker history & status feed** (Module 2.2) — strictly isolated to the logged-in
  user, with status badges and a chronological action timeline.
- **Central Admin Portal** (Module 3) — KPI dashboard, village-wise grievance volume,
  department breakdown, full filtering (village / department / status / urgency /
  date range / search), action & letter-generator panel (status update, official
  letter reference number, scanned letter upload, public remark vs. internal note),
  and CSV export (Module 3.3 — CSV instead of native .xlsx/.pdf binaries to keep the
  project dependency-light; it opens natively in Excel/Sheets).
- **CRITICAL: Village & Worker Data Isolation** — enforced at the application layer in
  `middleware/auth.js` (`isolationFilter`). Every query a worker/sarpanch makes against
  the `complaints` collection is scoped to `{ user: req.user._id }`. This is the
  Node/Mongo equivalent of the PostgreSQL Row-Level-Security policy described in SRS
  Section 7. Admin/MLA roles bypass the filter for full taluka visibility.
- **REST API** matching SRS Section 6 exactly:
  - `POST /api/v1/auth/send-otp`
  - `POST /api/v1/auth/verify-otp`
  - `POST /api/v1/complaints/create`
  - `GET /api/v1/complaints/my-history`
  - `GET /api/v1/admin/complaints`
  - `PATCH /api/v1/admin/complaints/:id/action`
  - (plus `POST /api/v1/auth/register` and `PATCH /api/v1/admin/workers/:id/verify`,
    which the SRS implies but doesn't spell out as endpoints)

## 2. What's intentionally simplified (and how to extend it)

| SRS ask | This build | To go to production |
|---|---|---|
| Firebase/Twilio OTP | Console-logged dev OTP | Set `OTP_MODE=twilio` and add credentials; the Twilio dependency is included |
| AWS S3 / Cloudflare R2 media storage | Local disk (`public/uploads/`) via Multer | Swap Multer's disk storage engine for `multer-s3` |
| SMS/push closed-loop notification | Console log on status change | Plug in Twilio/Firebase Cloud Messaging in `adminController.updateComplaint` |
| Excel/PDF export | CSV export | Add `exceljs` or `pdfkit` for native binary export |
| Offline buffering (mobile) | Not implemented (this is a responsive web app, not a native app) | A true offline-first experience needs a service worker + IndexedDB queue, or a native app shell |
| PostgreSQL RLS | MongoDB + application-layer isolation filter | If you migrate to Postgres, the schema in the SRS maps directly; enable the RLS policy shown in SRS §7 |

## 3. Prerequisites

- Node.js 18+
- A MongoDB instance — either:
  - Local: `mongodb://127.0.0.1:27017` (install MongoDB Community Server), or
  - Free cloud: [MongoDB Atlas](https://www.mongodb.com/cloud/atlas) — grab your connection string

## 4. Setup

### Safe Atlas demo seeder (recommended instead of the destructive seed)

Use `npm run seed:demo` to validate/preview the demo locally without connecting.
It uses the existing representative village list, five fictional role accounts,
and four text-only complaints. It creates no media files or OTP codes.

For an actual demo import:

1. Use an **empty, isolated demo database**, preferably `akole_ccms_demo`, not
   production. Stop other applications writing to this target during seeding.
2. Privately set `MONGO_URI` in `backend/.env` with that exact database in the URI
   path. This file is ignored by version control. Do not share credentials in chat.
3. Allow this machine's IP in Atlas and grant the database user the required
   database read/write/index permissions.
4. From the backend directory run:

<!-- // Generated by GitHub Copilot - Oct-16-2026 -->
```powershell
npm run test:seed
npm run seed:demo
node .\seed\demo.js --database=akole_ccms_demo --apply
```

The apply command checks that the entire target has no documents, then inserts
and verifies villages/users/complaints in an Atlas transaction. It never deletes,
replaces, or merges existing data. Rerunning after success is refused. Existing
empty collections/indexes may remain if setup fails; transactional document writes
are rolled back on failure. A network error during commit can have an uncertain
outcome: inspect the target before retrying. There is no non-transaction fallback.

Demo login placeholders: admin `9000000001`, MLA `9000000002`, worker `9111111111`,
sarpanch `9222222222`, unverified worker `9333333333`. These are not verified
recipient numbers: do not send real SMS to them. Use only an isolated controlled
demo with console OTP, never a public service containing real data. No login
secret or authentication bypass is inserted by the seeder.

For backend/Render testing, point the backend's `MONGO_URI` at the same demo
database; Android still uses the backend HTTPS API, not the Atlas URI. The
documented timeline-population fix is still needed for complaint decoding.

The older `npm run seed` below remains **destructive**; do not confuse the commands.

```bash
cd akole-ccms
npm install
cp .env.example .env
```

Edit `.env` and set `MONGO_URI` to your MongoDB connection string. Change `JWT_SECRET`
and `SESSION_SECRET` to random strings before any real deployment.

Seed the village master list and demo accounts:

```bash
npm run seed
```

This prints demo login numbers to your console, e.g.:

```
Admin:   9000000001
MLA:     9000000002
Worker (Sangvi):  9111111111
Sarpanch (Rajur): 9222222222
Worker (Kotul, unverified): 9333333333
```

Start the server:

```bash
npm start
# or, for auto-reload during development:
npm run dev
```

Visit **http://localhost:3000**. Log in with any demo mobile number above — the OTP
will print in your terminal (and also appear on-screen in dev mode).

## 5. Trying the isolation guarantee

1. Log in as the Sangvi worker (`9111111111`), submit a complaint, note the ticket ID.
2. Log out, log in as the Rajur sarpanch (`9222222222`) — you will only see your own
   history, never the Sangvi worker's complaint. Directly visiting the Sangvi worker's
   complaint URL (`/complaints/<id>`) returns a 404, not the data.
3. Log in as Admin (`9000000001`) — you'll see complaints from every village on the
   Master Dashboard.

## 7. Known limitations to be aware of

- This was built and reviewed without a live network connection, so `npm install`
  and a live MongoDB run haven't been executed in the build environment. The code
  follows standard, well-tested patterns (Express 4, Mongoose 8, Multer 1.4), but
  run `npm install && npm run seed && npm start` and watch your terminal for errors
  the first time you boot it.
- Voice recording depends on browser `MediaRecorder` support (all modern mobile/
  desktop browsers support it) and microphone permission.
- GPS capture depends on browser geolocation permission; the form still submits
  fine if the user declines it.
